# Safe update and release procedure

Weekly Actions checks official stable release metadata and opens a deduplicated review issue. It does not modify the pin or deploy. Dependabot proposes workflow updates. Scheduled Actions can be disabled by GitHub after prolonged repository inactivity; check the Actions page periodically.

1. Read upstream release notes, migrations, Dockerfile, entrypoint, database/encryption/Puma/Sidekiq configuration and hosting instructions. Resolve the new GHCR **index digest** and verify both Linux ARM64 and AMD64 manifests and the source commit. Never substitute `stable` or `latest` in the Dockerfile.
2. In a branch update `upstream.json` and the Dockerfile `FROM` together. Bump the wrapper version in `sure/config.yaml` and Dockerfile `BUILD_VERSION`; update changelog and source links. Consider `breaking_versions` for migrations needing manual attention. Keep the wrapper experimental until HAOS hardware acceptance is recorded.
3. Open a PR. Require Build and test success for metadata, runtime tests, native builds and isolated PostgreSQL/Redis smoke tests on **both** architectures. PRs have no package write step. Review changed upstream behavior, not only test results.
4. Rehearse an upgrade and coordinated backup restore against representative disposable data. Test HAOS installation, first account, CSV import, attachment persistence and Tailscale access on a test device. Do not use the production Pi without its owner's explicit deployment request.
5. Merge reviewed code. Main publishes only `sha-COMMIT` candidates. To publish a version, tag the reviewed commit `vVERSION` and push that tag. The tag workflow repeats both architecture tests, then assembles the multiarch version tag from tested images. It checks config/tag agreement and refuses to replace an existing release image. Never move Git tags or overwrite image version tags; issue a new patch version for fixes.
6. Confirm the GHCR package is **public**, linked to this public source repository, and both platforms can be pulled anonymously. A public Git repository does not automatically guarantee public GHCR visibility. Verify `docker buildx imagetools inspect ghcr.io/alexcode9/sure-homeassistant:VERSION` without credentials. If package permissions do not allow publication, stop here and resolve them; do not advertise the version as installable.
7. Create GitHub release notes with upstream version/digest, tests run, HAOS acceptance status, migration/backup requirements and known limitations. Only then recommend installing/updating through HA. Leave automatic updates off until real-world acceptance.

The initial `0.1.0` is an experimental container-tested release, not a claim that the user's Pi or production data has been tested. The repository metadata can briefly point at a not-yet-published version while a tagged release is building; do not install until its workflow and anonymous pull checks succeed.
