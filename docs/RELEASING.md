# Safe update and release procedure

Weekly Actions checks official stable release metadata and opens a deduplicated review issue. It does not modify the pin or deploy. Dependabot proposes workflow updates. Scheduled Actions can be disabled by GitHub after prolonged repository inactivity; check the Actions page periodically.

1. Read official Sure upstream release notes and changes in [the application fork](https://github.com/alexcode9/sure), including migrations, Dockerfile, entrypoint, database/encryption/Puma/Sidekiq configuration and hosting instructions. Build the reviewed fork commit on both platforms, resolve the fork GHCR **index digest**, and verify Linux ARM64/AMD64 manifests and their exact source commit. Never substitute `stable`, `latest`, `main` or an unpinned image in the Dockerfile.
2. In a branch update `upstream.json` and the Dockerfile `FROM` together, preserving the official upstream source/version and recording the fork source repository, build run and immutable image digest. Bump the wrapper version in `sure/config.yaml` and Dockerfile `BUILD_VERSION`; update changelog and source links. Consider `breaking_versions` for migrations needing manual attention. Keep the wrapper experimental until HAOS hardware acceptance is recorded.
3. Open a PR. Require Build and test success for metadata, runtime tests, native builds and isolated PostgreSQL/Redis smoke tests on **both** architectures. PRs have no package write step. Review changed upstream behavior, not only test results.
4. Rehearse an upgrade and coordinated backup restore against representative disposable data. Test HAOS installation, first account, CSV import, attachment persistence and Tailscale access on a test device. Do not use the production Pi without its owner's explicit deployment request.
5. Merge reviewed code. Main publishes only `sha-COMMIT` candidates. To publish a version, open **Actions → Publish verified Sure Finance release → Run workflow**, select `main`, enter the exact `sure/config.yaml` version (for example `0.1.1`) and type `RELEASE 0.1.1` in the confirmation field. This is an explicit manual approval: commits, PR merges and automated Dependabot updates cannot publish versioned releases. The workflow checks that `main` CI passed for the exact commit, refuses to overwrite existing tags/releases, creates `vVERSION`, and uses an explicit `workflow_dispatch` to start the tagged Build and test workflow. This dispatch is necessary because tags created with `GITHUB_TOKEN` do not themselves trigger `push` workflows. The tagged build repeats validation and PostgreSQL/Redis tests on ARM64 and AMD64, then assembles the version-tagged image. On an interrupted release, retry from the same commit: the workflow permits a pre-existing tag only if it points to that exact commit and requires successful tagged CI.
6. Confirm the GHCR package is **public**, linked to this public source repository, and both platforms can be pulled anonymously. A public Git repository does not automatically guarantee public GHCR visibility. Verify `docker buildx imagetools inspect ghcr.io/alexcode9/sure-homeassistant:VERSION` without credentials. If package permissions do not allow publication, stop here and resolve them; do not advertise the version as installable.
7. The manual release workflow verifies anonymous GHCR access and both target platforms before publishing the GitHub **prerelease**, including source commit, image and backup guidance. If any test, dispatch, or image check fails, no release is published; review the logs and retry only after fixing the issue. The tag is never moved or reused for different code. Review the generated notes, confirm the GHCR package is public, and record any HAOS acceptance findings. Only then recommend installing/updating through HA after a coordinated backup; leave automatic updates off until real-world acceptance.

The initial `0.1.0` is an experimental container-tested release, not a claim that the user's Pi or production data has been tested. The repository metadata can briefly point at a not-yet-published version while a tagged release is building; do not install until its workflow and anonymous pull checks succeed.
